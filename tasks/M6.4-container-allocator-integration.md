# M6.4 — Android container and allocator integration; M6 DoD
Status: done (runtime limits below) · Milestone: M6 · Needs phone: yes · Depends: M6.2, M6.3

## Why
M6 is complete only when the actual stock Android runtime boots and its
allocator works through the preserved kernel ABI.

## Steps
1. Apply the audited runtime mount/cgroup/container compatibility setup. Keep
   stock vendor and protected partitions unchanged; EFS must not become writable.
2. Start the real Android container, fix one evidenced blocker per test, and
   retain host USB SSH. Keep deferred hardware-service masks explicit; remove
   each only when its prerequisites exist. Re-evaluate the M6.2 diagnostic
   masks for `repowerd.service`, `a50-enable-autosuspend.service` and
   `sleep.target` with the PM-enabled config, recording any retained masks
   and their removal plan. The interface test is in
   [the M6.2 wakelock log](../log/2026-11-12-M6.2-wakelock.md).
3. Capture actual container getprop sys.boot_completed, allocator process
   state and ION allocation replay. M6.3 implements only the measured heap-0
   requests; the other six baseline reserved/secure heaps are unsupported.
   Check the real service's heap-query handling and allocation masks, and
   add heap support if new captured requirements demand it. DPU SysMMU v7.2
   provider probe passed, but no master attachment or device DMA is tested.
   If success depends on an unported M7
   component, prove the dependency and update the plan before expanding scope.
4. Evaluate every M6 DoD item and write the next milestone's tickets.

## Acceptance criteria
- [x] Android container sys.boot_completed=1, obtained through the normal runtime startup.
- [x] android.hardware.graphics.allocator@2.0-service running; captured ION requests replay successfully.
- [x] Stock vendor/protected-partition policy and USB SSH preserved; failed HALs and hardware limits documented.
- [x] M5 runtime masks (rild, ofono, bluebinder, a50-audio-route; `docs/05-plan.md` M5) re-evaluated with the container
      running: one boot without any of the four masks, recording systemd state, jobs and each unit's result. Every mask
      that no longer blocks multi-user is dropped from the built-in cmdline; every mask still needed is listed in STATUS.md
      with the evidence and the milestone that removes it (bluebinder M9, a50-audio-route M10, rild/ofono M11).
- [x] Baseline restored, pre-flight/fsck evidence saved, M6 DoD evaluated in STATUS.md with log and source/input hashes.

## Progress

Home-network SSH and baseline partition hashes verified on 2026-11-14.
Final test 7 reached normal boot property 1, with the real graphics
allocator running as guest PID 133 and registered over HIDL. Both ION ABIs
passed 32 captured requests each as Android UID 1000/GID 1003. Raw block
RO/WO/RW opens and mknod were denied; baseline negative control verified
the matrix detects an unrestricted policy. Vendor stayed ro/norecovery,
protected EFS filesystems unmounted, userdata rw and USB root SSH available.

All four M5 HAL masks are removed. Multi-user was reached at 212.21 s;
the late snapshot was degraded with zero jobs. Rild/ofono settled;
bluebinder still retries, and audio-route/lightdm fail as expected before
their hardware ports. No working Bluetooth/audio/modem/display is claimed.
Stock DTB/DTBO/BOOT hashes and baseline init's clean fsck passed after all
seven tests. M7 tickets are written; next is M7.1.

Runtime limits: a read-only per-boot RC bind defers the unported TEEGRIS
post-fs wait without faking Ready or editing vendor. Security-dependent
HALs and six reserved/secure heaps remain unsupported. Three power masks
remain after source review because automatic suspend is unvalidated;
removal must respect the existing M11 zero-mask gate. Legacy Android
task-profile warnings remain; native v2 is used, but QoS mapping is not
proven. Real display/GPU DMA remains M7.
