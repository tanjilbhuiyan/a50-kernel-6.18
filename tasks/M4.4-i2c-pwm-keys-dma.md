# M4.4 — I2C, PWM, keys, PL330 DMA
Status: blocked (real I2C controllers freeze 6.18) · Milestone: M4 · Needs phone: yes · Depends: M3

## Why
Mainline drivers exist for these (gap matrix category A, `docs/04-gap-matrix.md`). They are DT work, and S2MPB03 (M4.3) needs I2C.

## Facts / unknowns
- Stock DT: `samsung,s3c2440-i2c` and `samsung,exynos5-hsi2c` controllers, `samsung,s3c6400-pwm`, `arm,pl330` (`reference/stock-dt/dt.dtb.0.dts`, from :3548, :5286, :5349).
- Controller clocks must be in the 9610 CMU driver; which CMUs beyond M3.3's are needed is UNVERIFIED.
- Owner: no writes to any device on these buses without a named reason. sm5713 (charger, fuel gauge, MUIC) is left alone here.

## Steps
1. Add DT nodes and clocks; enable one block at a time.
2. I2C: probe only, using `i2cdetect` read mode, and compare addresses with the baseline's `/sys/bus/i2c/devices`.
3. Keys: report events from the volume and power keys.
4. PL330: driver probe and the dmatest self-test only if it is safe to run.

## Acceptance criteria
- [ ] I2C controllers probe; the devices found match the baseline's addresses.
- [ ] Volume and power keys produce input events.
- [ ] PWM and PL330 probe without errors.
- [ ] `log/<date>-M4.4-buses.md`.

## Progress (2026-11-10)
PWM probes (`pwmchip0`). `cmu_peri` works; the clock driver already had CMU_PERI.
**I2C freezes the phone:** 6.18 froze before the USB gadget twice, each needing a button reset and leaving no log: first with I2C 0/1/3/4/6, PWM and keys enabled, then with only I2C 0 and 1. Test 1 passed only because the driver failed early on a wrong pinctrl name, so it never touched the hardware. Cause unknown: `docs/08-open-questions.md` #8. **Do not boot `a50-bus` with those I2C nodes enabled** until this is understood.
Not tested yet: gpio-keys on its own (needs the owner to press keys), PL330 (needs CMU_CORE).

## Next attempt (owner, 2026-11-10: we will work on this again; needed before M7/M8: touchscreen on I2C 4 at 0x48, S2MPB03, others)
1. Separate the driver from the test: I2C driver on bus 0 only, and no `i2cdetect` in the init. No freeze means the bus traffic is the trigger, not the controller set-up.
2. Get a log out of a freeze: enable the hardware watchdog with a short timeout, so a frozen kernel resets without a button reset and the log may survive in memory. Unproven on this phone: one test first.
3. Then narrow down with the log. Suspects: an interrupt storm when the controller starts; a register access with its clock off.
Expect one or two button resets.
