# M4.7 — CPU frequency via ACPM DVFS
Status: todo · Milestone: M4 · Needs phone: yes · Depends: M4.1, M4.2, M4.6

## Why
M4 DoD: cpufreq scaling between min and max.

## Facts / unknowns
- 4.14 DVFS: `drivers/soc/samsung/cal-if/acpm_dvfs.c`, `fvmap.c`, compatible `samsung,exynos-acpm-dvfs`; ACPM channel 5 (`reference/stock-dt/dt.dtb.0.dts:3047`). The stock DT also has `samsung,exynos-dvfs-manager` (:4457).
- Mainline has no 9610 CPU DVFS driver. New work: a small cpufreq driver or provider on top of M4.2.
- The boot clock is unknown; `docs/07-risks.md` records the earlier slow-CPU theory as retracted. Measure it.
- **Risk:** this changes CPU voltage and frequency through firmware. A bad table can hang the phone.

## Safety rules
- Use only frequency/voltage tables the firmware itself reports (`fvmap`), never invented values.
- Read the current rate and tables first, with no change. Any frequency change is a separate test, shown to the owner first.
- M4.6 thermal must be working first.

## Steps
1. Read the DVFS domains and tables through ACPM, read-only; compare with the baseline's `scaling_available_frequencies`.
2. Add the driver with one conservative frequency change on one cluster.
3. Extend to both clusters, then to min and max.

## Acceptance criteria
- [ ] `scaling_available_frequencies` matches the baseline for both clusters.
- [ ] Frequency changes between min and max are measured, not just requested (a timing loop).
- [ ] No hang or thermal trip in a load test.
- [ ] `log/<date>-M4.7-cpufreq.md`.
