# M6.2 — Binder, native ACK ashmem and Android core interfaces
Status: in-progress · Milestone: M6 · Needs phone: build no / test yes · Depends: M6.1

## Why
Stock Android 11 userspace needs binder contexts and ashmem. ACK 6.18 retains
ashmem as a Rust driver; use the native ACK interfaces and pinned toolchain.

## Steps
Start with the [M6.1 isolated BinderFS control and candidate](../log/2026-11-11-M6.1-android-runtime-abi-audit.md#first-m62-test--isolated-binderfs).
Use the same per-boot `mount-android-partitions.service` mask for both boots
and capture the config delta, device paths and `BINDER_VERSION` before adding
ashmem, sync or PM options in separate tests.

1. From the audit, enable the necessary binder/binderfs, Rust ashmem, sync_file,
   sw_sync and wakelock options. Expose the node paths expected by vendor
   userspace using native mechanisms; record any compatibility setup.
2. Build with the pinned ACK Rust/clang tools; verify resolved config, tool
   versions, Image budget and the unchanged UFS guard. Keep USB SSH working.
3. Test interface open/ioctl behavior and expected binder contexts, capturing
   actual output on 6.18. Preserve clean source versus diagnostic branches.

## Acceptance criteria
- [ ] Reproducible config/build and the required interface/node availability on 6.18.
- [x] Functional binder/ashmem smoke tests with failures explained; no claim of full container startup yet.
- [ ] USB SSH and userdata protection retained; baseline restored and saved fsck checked.
- [ ] Log, hashes and source commits/patches recorded.

## Progress

BinderFS control and candidate passed. The three candidate context devices
all reported protocol 8. USB SSH and userdata protection held, and each stock
restore passed pre-flight and the saved fsck check. Native ACK Rust ashmem
passed the AArch64 size ioctl and shared mmap test in a separate boot, with
Binder, USB SSH and the userdata guard verified again. Native sync fences
passed the two-timeline merge and signal test with Binder and ashmem
regression checks and a verified stock restore. Next is the userspace
wakelock interface in a separate diagnostic boot.
