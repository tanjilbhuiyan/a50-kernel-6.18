## Result: the TOP→DISPAUD clock is off, switched off by our 6.18 clock init

- The DISPAUD domain is on (status `0x3000f`).
- The TOP gate `CLKCMU_DISPAUD_DISP` (`0x12100000 + 0x2040`) reads `0x00100000`. That is manual mode (bit 20) with the
  manual clock value at 0 (bit 21) and automatic gating off (bit 28). So the display blocks have no clock, and the probe
  correctly didn't read them.
- **Cause, from source plus the boot log:**
  - `exynos_arm64_init_clocks()` enables automatic gating only when the CMU register range is exactly 0x10000
    (`samsung_is_auto_capable`, `clk.c:247-260`). Our DT gives `cmu_top` `reg = <0x12100000 0x8000>`, which is the size
    Samsung's CAL also uses (`cmucal-sfr.c:11`).
  - The boot log shows `clock-controller@12100000: incorrect res size for automatic clocks`, and the same for the USB and
    FSYS CMUs.
  - In that case the driver sets `GATE_MANUAL` and clears `GATE_ENABLE_HWACG` on **every** gate register, keeping only the
    manual value (`clk-exynos-arm64.c`, the `!init_auto` branch).
  - A clock that ran on demand under automatic gating, and that no driver enables, is therefore off from 0.000 s.
    `clk_ignore_unused` doesn't help, because no `clk_disable` ever happens.
- **Inference (unverified):** S-Boot left this gate under automatic gating. 6.18 can't observe the value from before its own
  clock init.
- **Consequences:**
  - The panel still shows the last bootloader image only because a command-mode panel holds its frame in its own memory.
    This is also why the screen stays on the boot warning screen during every 6.18 boot.
  - The same rewrite applies to the TOP gates for G3D (`gout_cmu_g3d_switch`) and G2D. M7.3's G0 must check them too.

## Incident: USB lost, then manual recovery, so there is no timed dump

- 6.18 answered SSH until 03:58:03. At about 03:59 the owner reported the warning screen, and no USB device was visible
  (checked 03:59:08 to 03:59:51).
- Claude asked for manual recovery (Volume Down + Power, then Volume Up + Volume Down while plugging in USB). The phone
  reached Download mode before 04:01:38, when the runner restored stock automatically.
- **This was premature.** The warning screen is what every 6.18 boot shows (see above), and the runner's 540 s window
  (until about 04:02:20) and the 420 s dump timer (about 04:00:45) hadn't expired. The forced restart probably threw away
  the timed dump. Whether 6.18 had reset or only lost USB is **unverified**:
  - the runner found no dump in `last_kmsg`;
  - the S-Boot records in `last_kmsg` are partly corrupted and don't give a clear reset reason
    ([excerpt](../reference/m72-display/d0-sboot-reset.txt)).
- **Rule from now on:** while the runner is inside its WAIT window, the warning screen and a missing USB device are not
  grounds for manual recovery. Recover by keys only after the runner prints its "NO Download mode" timeout message.

## Next single variable (proposal: D0b)

Keep D0 as it is, and add one change: before reading, the probe enables only the TOP gate `gout_cmu_dispaud_disp`
(`CLK_GOUT_CMU_DISPAUD_DISP`) through the clock framework, logs the gate value before and after, and then runs the same
read-only reads.

Alternative: give the CMU nodes a 0x10000 range so the driver uses automatic gating, as mainline intends. That changes
every TOP, USB and FSYS gate at once (UFS and USB included), so it is not a single display variable.
