# 2026-11-10 M5.3 Halium's own init boots ubuntu.img to systemd

## Review of what Halium's init writes (step 1)
Sources: embedded ramdisk /init (src/m37/halium-root/f123) and /scripts/halium (f116).
- userdata (inside the guard's allowed range): mke2fs only if the first 4 KiB are zero (not the case: ext4 superblock present); mount + umount (journal replay), `e2fsck -y`; resize2fs only if the partition exceeds the filesystem by > 10000 KiB (not the case: filesystem 13745152 blocks = partition); property files under android-data; mount with `discard,data=journal`.
- mount_android_partitions reads `${rootmnt}/var/lib/lxc/android/rootfs/fstab*`: none exists on the baseline (checked over SSH).
- The A50 patch in /init starts `/root-rescue2.sh` if present, else /sbin/init: the file does not exist in ubuntu.img (checked), so systemd runs.
- Baseline (4.14) mounts, read over SSH: userdata rw; ubuntu.img (loop0) ro as /; Android system (loop1) ro; vendor sda26 ro; CPEFS sdd1 ro; **EFS sda3 rw** (stock behaviour on 4.14, mounted by the Android side). On 6.18 the guard refuses every write outside userdata, so EFS cannot change: expect ext4/IO errors for sda3, not data changes (CLAUDE.md rule 5 enforced in the kernel).
- Discard: userdata is mounted with `discard`; UNMAP stays blocked by the guard.
