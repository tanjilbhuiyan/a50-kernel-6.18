## Candidate source

An isolated worktree was created at `src/m73/g2b-kernel`, branch
`a50-m73-g2b-wip`, from the tested GPU commit
`c04d5ada5e58173d61e2bbf634b0a17cea98c0a6`. The shared checkout was not
switched. Candidate edits remain uncommitted in that worktree; clean
production branches are unchanged.

The functional fix removes the Samsung `MALI_SEC_INTEGRATION` page-table
walk in `kbase_cancel_soft_job()`. The atom is kernel memory, and its
context's process mm can be gone during teardown. The original fence/event
cancellation switch is retained; returning early on a missing mm would
silently lose cleanup and is not the fix.

The only other kernel changes are passive display diagnostics:

- `g2b_stats` read-only sysfs snapshot at
  `/sys/devices/platform/148b0000.decon_f/g2b_stats` reports the actual
  release/retire fence context, sequence, queue depth, layer-count histogram,
  active formats, existing DMA/CPU-copy counters, completed updates and the
  worker's current stage. It takes no hardware lock, so a blocked worker
  does not block the snapshot. Counter fields are asynchronous observations.
- Sampled WIN_CONFIG/acquire logs identify output and input fence contexts,
  layer count, format and DMA eligibility. Only the first eight sequences
  and every 128th sequence are sampled, to limit log pressure.
- Existing early/late display reports include fence owner/worker state.
  The driver name is `a50-decon`; its actual timeline callback returns
  `decon_f`. Context numbers must be measured on the new boot.

No fence is signaled early, no acquire wait is skipped or shortened, and
no DMA/CPU-copy routing, format, geometry, clock or power behavior changes.
The display theory remains unverified until the phone test supplies data.

## Prepared live procedure

`tools/m73/run_g2b.sh` verifies inputs, uses the established
DTB/DTBO/BOOT runner and always waits for stock restoration. Once USB SSH
is verified, it streams kernel messages and snapshots display state/IRQs
every two seconds to ignored host files, preserving evidence even if the
client or kernel fails.

`collect_g2b.sh` requires the metadata gate off, `/dev/mali0` and the new
stats file. It records hashes of the installed clients and runs
`/usr/bin/test_egl` (12 s limit) then `test_glesv2` (30 s limit), both
through a login bash that must supply the known static-TLS setting.
The client timeout/cancellation is intentional to exercise the regression.
Exit status, post-cancel uptime, worker state, IRQs and runtime/storage
observations are captured. A late snapshot and saved baseline fsck follow.
Raw phone output stays under ignored `src/m73/g2b-raw/` until redacted.

## Phone test and results

Owner confirmed presence, USB connected and Claude Code idle for G2b.
Fresh baseline pre-flight passed at about 01:50: kernel 4.14.194, stock
DTB/DTBO/BOOT hashes match, home `192.168.0.171`, battery 100% Full.
Flash 01:51:22; USB root SSH verified 01:52:17. Phone wall-clock client
markers differ from the host clock; use kernel uptime/host runner times
when aligning these captures.

**Cancellation regression:** `test_egl` exited 139 (userspace SIGSEGV),
and `test_glesv2` reached its 30-second limit (exit 124). Kernel uptime
continued, USB remained usable and the normal 420-second dump ran; the
old cancellation panic did not recur. Both clients received the required
GLIBC_TUNABLES setting. The EGL userspace crash remains a separate issue;
the collector records client statuses directly rather than masking them
through a pipeline.

**Fence ownership:** sysfs and the late kernel report directly identify
context 1 as driver `a50-decon`, timeline `decon_f`. All 603 guilty-fence
warnings in the continuous kernel stream are on context 1, with sequences
376 through 1735. The display queue continues progressing and drains:
final sequence 1800, 1800 worker completions, pending zero, stage idle.
The sampled peak pending count is 255. Completions here mean the worker
reached release signaling; they are not proof of visible pixels.

**WIN_CONFIG:** 1815 requests comprise 15 empty and 1800 single-buffer
configurations. The sampled format is 2. Final path counters are 1800
fallbacks and 1800 skipped layers, **zero CPU copies and zero DMA scanouts**.
Acquire-fence timeout count is zero. The sampled input GPU fences have
their signaled bit set; the long waits are on display output fences.
Thus slow CPU pixel copying is not the cause demonstrated by this run.

Stock source confirms format 2 is RGBA_8888, which the current handover
driver does not support. It also shows a format-to-DPP byte-order
translation that a fix must honor; simply treating the ABI value as the
hardware encoding is unsafe. See `reference/m73-gpu/g2b-format-analysis.md`.

**Owner observation:** black/flicker only, no recognizable scene. This
agrees with buffers being skipped but does not prove GPU rendering.
The GPU job interrupt has activity; that alone is not frame-correctness
evidence. M7.3's execution/rendering acceptance remains incomplete.
