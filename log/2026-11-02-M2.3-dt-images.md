# 2026-11-02 M2.3 DTB/DTBO partition images in stock dt_table format
Variable changed: none (host-only; nothing flashed)
Inputs: stock `reference/stock-images/dt.img` (`59209aa5…`) and `dtbo.img` (`40e47ed1…`); A50 DTB from kernel commits `4fd044c7c` + `42664a3c5` (branch `a50-dt`, `src/ack-6.18/common`); `tools/dt_table.py`.
Flashed: nothing
Findings about the stock images (new evidence, `tools/dt_table.py info`):
- dt.img: 1 entry (dt_size 134776, id 0, rev 0, custom0/1 = 0x0/0xff = hw_rev window). dtbo.img: 6 entries, custom0/1 = hw_rev..hw_rev_end: 0/0, 1/1, 2/2, 3/3, 4/5, 6/0xff. Entry 5 is the one for revision 6 (`androidboot.revision=6`, `dtbo_idx=5`). The same window is also inside the FDTs as root properties `dtb-hw_rev[_end]` / `dtbo-hw_rev[_end]`.
- Both images are NOT just a dt_table: after the table (total_size) comes a 528-byte Samsung signature block (`SignerVer02…`), then an AVB0 vbmeta blob at 4 KiB alignment (dt.img @139264, dtbo.img @659456, 2112 B) and a 64-byte `AVBf` footer at the very end of the 8 MiB partition. Stock DT root has `dtb-hw_rev = <0>`, `dtb-hw_rev_end = <0xff>`, which the M2.1 DT lacked: added (kernel commit `42664a3c5`, documented in samsung-boards.yaml, dt-validate clean).
Decisions:
- Layout (a): our complete DTB in dt.img entry 0; dtbo.img entry 5 replaced by a no-op overlay (`reference/dt-6.18/dtbo-a50-rev6-noop.dts`: same compatible and hw_rev 6..0xff, no fragments). Why: the stock overlay's fragments target `0xffffffff` phandle placeholders that only resolve against the Samsung base tree's symbols; applying it to our minimal DTB would likely fail or mis-merge. Option (b) rejected for that reason (inference from the overlay contents, not a tested S-Boot behaviour). Entries 0-4 of dtbo.img left as stock.
- Replaced blobs are zero-padded to the stock dt_size, so every header/entry field, total_size and all offsets are identical to stock and the signature block / vbmeta / footer stay at their original offsets, byte-for-byte. Only the two FDT payloads differ. (An unpadded variant is available via `--no-pad` for a later one-variable test.)
- The Samsung signature, vbmeta hash and AVB footer are carried over STALE (they describe the stock content). Whether S-Boot checks them on DTB/DTBO is UNVERIFIED; vbmeta partition flags=3 disables AVB verification for the OS, but the Samsung `SignerVer02` check is a separate bootloader matter (R9). Settled only in M2.4.
Observed:
- `roundtrip` on stock dt.img and dtbo.img: IDENTICAL (output hashes equal the pinned `59209aa5…`/`40e47ed1…`). `build --set N=<own blob>` also reproduces each stock image exactly (padding path exercised).
- Ours: `reference/dt-6.18/images/dt.img` sha256 `b09210d1…4ea7`, `dtbo.img` sha256 `6d81cce8…51fe` (full values in `SHA256SUMS`). Both 8,388,608 B (exactly the partition size). Region diff vs stock: header+entries identical, tail identical, dtbo entries 0-4 identical; changed: dt entry 0 and dtbo entry 5 payloads only. Our DTB re-extracted from the image decompiles (8 cpus, model, hw_rev); fdt totalsize 3665, remainder zeros.
Rollback (to run in M2.4 with the owner present, TWRP + adb; partitions per docs/01-device.md: DTB = sda12, DTBO = sda13; confirm the by-name links on the phone first, unverified here):
1. Before writing: `adb shell dd if=/dev/block/sda12 of=/tmp/dtb.bak` and sda13 likewise; `adb pull`; sha256 must equal `59209aa5…` / `40e47ed1…` (else stop).
2. Write ours: `adb push images/dt.img /tmp/`, `dd if=/tmp/dt.img of=/dev/block/sda12 bs=1M`; read back `dd if=/dev/block/sda12 bs=1M count=8 | sha256sum` == source hash. Same for dtbo.img -> sda13.
3. Roll back: write `reference/stock-images/dt.img` / `dtbo.img` the same way, read back == `59209aa5…` / `40e47ed1…`. BOOT fallback `baseline/…/boot.img` (`7d5855ef…`) via Heimdall as usual.
Result: PASS for the host-side criteria. Not verified: that S-Boot accepts these images.
