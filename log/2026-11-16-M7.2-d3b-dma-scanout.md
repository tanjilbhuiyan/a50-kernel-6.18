# 2026-11-16 M7.2 boot D3b: DMA scanout of WIN_CONFIG buffers through the SysMMU

Session by Claude Code. The phone was on the home network at `192.168.0.171`; Codex was idle; the backup hash matched.
- The first flash attempt was blocked by Claude Code's automatic safety check before anything ran (no runner started,
  phone stayed on the baseline).
- The owner then said "present, flash D3b", and the cycle ran.

## Change and build

- **The single variable compared with D3a2:** kernel commit `97c03597f` on `a50-m72-d3b-test`
  ([patch](../reference/m72-display/0010-TEST-ONLY-a50-decon-scans-out-WIN_CONFIG-buffers-by-D.patch)). The DT is unchanged
  (`src/m72/dt-d3a.img`).
- **DMA path:** a single full-screen 8888 BUFFER window (`src`/`dst` 1080x2340 at 0,0; stride 1080) is mapped on the
  display device with `dma_buf_attach()` and `dma_buf_map_attachment_unlocked(DMA_TO_DEVICE)`. The driver checks that the
  IOVA range is contiguous and 32-bit. IDMA0, which feeds window 3 as S-Boot set it up (D0c), is reprogrammed in the 4.14
  `decon_update_regs()` order:
  1. wait for the previous `SHADOW_REG_UPDATE_REQ` to clear;
  2. write `IDMA_IN_BASE_ADDR_Y` and the `IDMA_IN_CON` format field (bits 16:11);
  3. request the shadow update for all windows (`0x3f`) plus global;
  4. send one frame.

  The previous buffer is unmapped and released only after the frame that replaces it is done.
- **Fallback:** any other configuration, and `FBIOPAN_DISPLAY`, points IDMA0 back at the boot framebuffer (CPU copy for
  WIN_CONFIG, as before).
- **Config and initramfs** are byte-identical to M6.4 test 7. The guard and sense host tests pass.
- **Image:** BOOT `src/m72/boot-d3b.img`, sha256 `0d3ccbe80b7559659839a1b9852306de4c5d36c258fd4bac6bf3a5c7d956a15a`.
  Inputs in [d3b-inputs.json](../reference/m72-display/d3b-inputs.json).
- **Test:** `tools/m72/winconfig_test.c` adds test 4, which flips 30 times between the test-1 buffer and a second ION buffer
  (yellow left half, blue right half), waiting for each retire fence, and ends on the second buffer.

## Result: PASS

- **Live over USB SSH** ([d3b-live.txt](../reference/m72-display/d3b-live.txt)):
  - SysMMU translation on: `MMU_CTRL=0x00000005`, `PT_BASE=0x00881190`, identity map intact.
  - Test output:

    ```
    test1: retire signalled after 25.5 ms; rel signalled        (D2b-D3a2 CPU copy: ~305 ms)
    test2: empty config retire_fence=-1 (expect -1)
    test3: before acquire signal: unsignalled; after: signalled in 14.0 ms
    test4: 30 flips in 504.8 ms, 16.8 ms per frame, 0 over 100 ms
    RESULT: PASS
    --- faults: 0
    ```

  - 16.8 ms per frame is 60 Hz: each flip waits for one TE.
- **Owner:** the screen ended on "yellow left and blue right", the last flipped buffer.
- **Late log** at 414.7 s: `frames req=33 done=34 … timeouts=0 extra=0 te=24838 FRAME_COUNT=36 win_configs=33 copied=0
  skipped=0 acq_timeouts=0 frame_wait_timeouts=0 scanned=32 dma_fallbacks=0 shadow_wait_timeouts=0 IDMA0=0xfe000000`.
  - All 32 buffer frames were DMA scanouts; none were copied.
  - IDMA0 still holds the last buffer's IOVA, `0xfe000000`, at the top of the 32-bit IOVA space where iommu-dma allocates.
  - No fault, SError, BUG or SysMMU lines in the dump window ([dump](../reference/m72-display/d3b-dump.txt)).
- **Restore:** post-flight passed; fsck clean, 6521 files ([run](../reference/m72-display/d3b-run.txt), [fsck](../reference/m72-display/d3b-baseline-fsck.txt)).

## Limits

- Scanout uses one window, IDMA0/window 3, and only a full-screen 8888 buffer. Multiple layers, positioned or scaled
  layers and YUV fall back to the CPU copy. Real multi-window DPP programming isn't ported.
- The stock composer's own WIN_CONFIG traffic is still unexercised, because nothing renders yet (needs M7.3).
