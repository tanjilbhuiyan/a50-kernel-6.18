## Change and build

- **The single variable compared with D0c:** kernel commit `3a9d3da33` on `a50-m72-d1-test`, on top of `6680c9674`
  ([patch](../reference/m72-display/0004-TEST-ONLY-D1-requests-one-command-mode-frame-from-th.patch)). 30 s after boot it:
  1. enables `gout_dispaud_smmu_dpu_clk` (the DPU SysMMU stays in bypass; no device is attached);
  2. fills the boot framebuffer at `0xca000000` (1080x2340, 4 bytes per pixel) with four horizontal bands, written as
     a8r8g8b8 red, green, blue, white;
  3. requests one command-mode frame like `decon_reg_update_req_and_unmask()` (`cal_9610/decon_reg.c:1910-1916`):
     `SHADOW_REG_UPDATE_REQ` bit 31, then `HW_TRIG_EN` set and `HW_TRIG_MASK_DECON` cleared;
  4. after 100 ms, masks the trigger again (`decon_reg_set_trigger(DISABLE)`).

  Results are logged and repeated at about 405 s for the dump.
- **Config and initramfs** are byte-identical to M6.4 test 7. The guard and sense host tests pass.
- **Image:** BOOT `src/m72/boot-d1.img`, sha256 `a9f681eebf2f9f44a48e7596a8b98a20d1600df148f91356d555b969d2e2b15a`.
  Inputs in [d1-inputs.json](../reference/m72-display/d1-inputs.json).

## Result: PASS

- **Owner observation:** the warning screen changed to "four horizontal bands (red, green, blue, white)". This is the
  first image 6.18 has sent to this panel.
- **Logged values** ([d1-probe.txt](../reference/m72-display/d1-probe.txt), from the [dump](../reference/m72-display/d1-dump.txt)):

```
d1: enable gout_dispaud_smmu_dpu_clk ret=0
d1: before GLOBAL=0x00000133 TRIG=0x00003010 FRAME_COUNT=3
d1: after FRAME_COUNT=9 (+6) GLOBAL=0x00000113 PENDING=0x00003000 SHADOW=0x00000000 TRIG=0x00003010
d1: idma0 ENABLE=0x00000004 IRQ=0x000003f6 CFG_ERR=0x00000000
```

- **What the values show:**
  - While unmasked for 100 ms, DECON sent 6 frames on TE, which fits about 60 Hz.
  - At the 100 ms read it was running (`GLOBAL` idle bit clear) and IDMA0 was busy (`IDMA_OP_STATUS`).
  - The shadow request was consumed (`SHADOW` = 0).
  - The trigger is masked again (`0x3010`).
  - IDMA0 reported no configuration error.
- **Pixel format:** the colours appeared in the written order, so the boot framebuffer is **a8r8g8b8**. That closes the
  framebuffer-format risk accepted in M2.1 (`log/2026-11-01-M2.1-dt.md`).
- **Faults:** the dump window has no fault, SError, BUG, WARNING or SysMMU fault lines.
- **Restore:** rollback at 13:53:36, then 4.14 up since 13:53:50. Post-flight passed (stock DTB/DTBO, baseline BOOT).
  Baseline fsck clean: 6521/3440640 files, 1986839/13745152 blocks ([d1-baseline-fsck.txt](../reference/m72-display/d1-baseline-fsck.txt)).
  Run transcript: [d1-run.txt](../reference/m72-display/d1-run.txt).

## Meaning for the port

- S-Boot leaves a complete command-mode pipeline: DECON, window 3, IDMA0 at the boot framebuffer, DSI link, panel.
- 6.18 can drive frames over it with three things: the TOP display clock and the SysMMU clock enabled through the clock
  framework, plus the stock update/trigger sequence. No PHY, panel power or SysMMU translation is needed for that.
- **Next (D2 in the M7.1 plan):** the fbdev DPU20 core. Expose `fb0` with the stock `S3CFB_*` ioctls on top of this
  handed-over state, with the EA8076 panel treated as already on and SysMMU still in bypass. Do it in steps, starting
  with a driver that owns the clocks, DECON trigger and vsync IRQ and turns `S3CFB_WIN_CONFIG` buffers into frames. This
  is a substantial forward-port (M7.1 sizes dpu20 at about 36k lines); start from the 9610 CAL plus the decon/dpp/dsim
  core and drop DisplayPort, ABD, MDNIE, DPUI and BTS.
