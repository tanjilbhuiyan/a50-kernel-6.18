# 2026-11-16 M7.2 boot D2b: S3CFB_WIN_CONFIG with stock fences

Session by Claude Code. The owner confirmed being present right before the flash; Codex was idle. The outer repo was at
`487a50a`. The phone was on the office network at `192.168.181.225`, battery 100%. The `ubuntu.img` backup hash matched.

## Change and build

- **The single variable compared with D2a2:** kernel commit `b7e58452f` on `a50-m72-d2b-test`, on top of `cd08e9304`
  ([patch](../reference/m72-display/0007-TEST-ONLY-a50-decon-S3CFB_WIN_CONFIG-with-stock-fence.patch)).
  The DT is unchanged (`src/m72/dt-d2.img`).
- **ABI:** the stock argument `decon_win_config_data`, laid out as 4.14 `dpu20/decon.h` and `cal_9610/decon_cal.h` with
  `MAX_DECON_WIN` = 4 and enums as 32-bit fields. A `static_assert` checks the 1040 bytes on arm64, which gives
  `_IOW('F', 209, …)` = `0x441046d1`, the value captured from the stock composer in M1.3.
- **Fence model, as in 4.14 `decon_set_win_config()` and `fence.c`:**
  - one fence per call, returned as `retire_fence` and as `rel_fence` of every BUFFER window (`decon_create_release_fences`);
  - `retire_fence = -1` when no window is active;
  - buffer and acquire-fence fds are referenced with `dma_buf_get()` and `sync_file_get_fence()`, never closed by the
    kernel.
- **Temporary CPU bridge** until the SysMMU attach (D3): an ordered worker waits up to 1 s per acquire fence, copies each
  BUFFER layer into the boot framebuffer, sends one frame, and signals the fence after frame-done or 100 ms.
  - Supported: 8888 formats (`ARGB/XRGB` as-is; `ABGR/XBGR` with red and blue swapped). No scaling or blending.
  - Anything else is logged and skipped.
  - The format naming follows the IDMA word order: the boot window uses `IDMA_IMG_FORMAT_ARGB8888` (IN_CON bits 16:11 = 0),
    and D1 showed the word `0xffff0000` displays red.
- **Config and initramfs** are byte-identical to M6.4 test 7. The guard and sense host tests pass.
- **Image:** BOOT `src/m72/boot-d2b.img`, sha256 `92fccfdf7d7cae5f6e90100e0b13e3d57021337deb322475813630c4ebb0084b`
  ([inputs](../reference/m72-display/d2b-inputs.json)).
- **Test tool:** `tools/m72/winconfig_test.c` (static NDK binary). It allocates a full-screen buffer from `/dev/ion` heap 0
  (M6.3 ABI), draws in Android byte order with format `ABGR_8888`, and runs three cases.

## Result: PASS

- **Live over USB SSH** at about 50 s ([d2b-live.txt](../reference/m72-display/d2b-live.txt)):

```
test1: retire_fence=6 rel_fence=7 remained=1
test1: retire signalled after 307.1 ms; rel signalled
test2: empty config retire_fence=-1 (expect -1)
test3: before acquire signal: unsignalled; after: signalled in 315.8 ms
RESULT: PASS
```

- **Owner observation:** "magenta to cyan gradient on top, checkerboard at bottom", exactly the buffer contents, with the
  colour order right.
- **Late log** at 414.7 s: `frames req=3 done=4 … timeouts=0 extra=0 te=24796 FRAME_COUNT=6 win_configs=3 copied=2
  skipped=0 acq_timeouts=0 frame_wait_timeouts=0`. No fault lines in the dump window ([dump](../reference/m72-display/d2b-dump.txt)).
- **Latency:** about 300 ms per frame. That's the CPU copy (2.5 million `writel_relaxed` with a byte swap into the
  write-combined boot framebuffer), not DECON. D3 replaces it with DMA scanout.
- **Restore:** post-flight passed; 4.14 up since 15:38:54; fsck clean, 6521 files
  ([run](../reference/m72-display/d2b-run.txt), [fsck](../reference/m72-display/d2b-baseline-fsck.txt)).
