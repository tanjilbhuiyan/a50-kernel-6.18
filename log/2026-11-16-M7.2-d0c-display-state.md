## Corrections to the D0 log and the M7.1 audit

The test DT (`src/m63/dt-sysmmu.img`, `exynos9610-a50-sysmmu.dts` at `bd3fe49b2`) **does** instantiate `cmu_dispaud` (range
0x8000) and the DPU SysMMU, whose clock is `CLK_GOUT_DISPAUD_SMMU_DPU_CLK`. Two consequences:

- The 6.18 clock init also forced the CMU_DISPAUD gates into manual mode. Their clock values stayed on (`0x00300000`).
- The SysMMU driver uses that clock chain, so its probe-time enable/disable may be what left the TOP gate and
  `GAT_SMMU_DPU` off. This is **unverified**: the value from before 6.18's init isn't observable.

The D0 statement that CMU_DISPAUD is "not registered by 6.18" holds only for the base DT, not for the DT used in these tests.

## What this means for D1 (the first frame update)

Everything except the trigger is already set up by S-Boot. DECON is enabled in command mode, window 3 reads the boot
framebuffer at `0xca000000` through IDMA0, and the DSI link is configured. A frame update therefore needs:

1. the display clocks on (shown in D0b/D0c);
2. the **DPU SysMMU clock on** before any DMA, because IDMA traffic passes the SysMMU even in bypass. Running DMA through
   a clock-gated SysMMU risks a bus stall;
3. a pattern written into the boot framebuffer;
4. Samsung's command-mode start sequence: `SHADOW_REG_UPDATE_REQ` global (bit 31), then `HW_TRIG_EN` set and
   `HW_TRIG_MASK_DECON` cleared (`decon_reg_set_trigger()`, `decon_reg.c:1888`), then the mask restored after the frame.
   Whether IDMA0 must be re-enabled per frame is to be checked in the DPP CAL first.

Pass evidence: `FRAME_COUNT` increases, and the owner sees the pattern on the panel.
