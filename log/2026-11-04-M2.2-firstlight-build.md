What the init does (`reference/m22/init.txt`): mounts proc/sysfs/devtmpfs, prints to tty0 (framebuffer console) and `/dev/kmsg` (so it reaches pstore): banner and kernel version, uptime/CPUs, S-Boot's command line, DT model, memory, whether /a50-marker exists (ramdisk passed?), then mounts pstore and shows any records from the PREVIOUS boot, greps psci/ramoops/simplefb/GIC/timer lines, the first 25 lines of /proc/iomem, a 45 s visible countdown, then `echo c > /proc/sysrq-trigger` (deliberate panic so the NEXT boot has a crash record), falling back to `reboot -f`. Reading a crash therefore needs two boots of this image.
Risks and unverified items for M2.4 (first light), none of them testable on the host:
1. Load address: the 6.18 Image header has text_offset 0 (the 4.14 baseline has 0x80000; both set the "placement anywhere" flag) while kernel_addr 0x10008000 is not 2 MiB-aligned. The baseline boots from that address, so S-Boot does not care, but whether a 6.18 kernel does is unknown. Header kept identical to change one variable; a 2 MiB-aligned kernel_addr (e.g. 0x10200000) is the ready second variable.
2. Framebuffer pixel format/stride is assumed (M2.1); the DT in dt.img still carries ramoops@f9d10000, which M1.5 showed empty: change it to 0x91388000 (node text in the M1.5 log) and rebuild dt.img before M2.4.
3. Restart: PSCI is described as plain `arm,psci` v0.1 with explicit function IDs; SYSTEM_RESET is not known to work, so after the panic the phone may hang instead of rebooting (owner then holds Vol Down + Power; whether DRAM survives that reset is unknown, which is exactly what the two-boot test measures).
4. S-Boot patches the DT it passes (memory, chosen/initrd); the kernel behaviour with the A50 DT is untested.
5. Nothing was verified on hardware: S-Boot acceptance of this image is unverified until M2.4.
