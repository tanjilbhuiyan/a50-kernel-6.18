# 2026-11-04 M1.5 working crash log across a reboot
Variable changed: one controlled kernel panic on the baseline (runtime-only: sysrq enabled for the test, reverts at reboot). Nothing flashed.
Inputs: baseline phone (BOOT `7d5855ef…` verified), kernel 4.14.194 Mint-user, root SSH over Wi-Fi 192.168.0.171, owner present.
Step 1 (read-only) findings:
- pstore mounted (`pstore on /sys/fs/pstore`), empty before the test. Config: PSTORE, PSTORE_CONSOLE, PSTORE_PMSG, PSTORE_RAM, PSTORE_ZLIB_COMPRESS, DEBUG_SNAPSHOT (+ many DEBUG_SNAPSHOT_* items), SEC_DEBUG*, EXYNOS_DEBUG, FTRACE (no syscall tracing).
- `ramoops.0` platform device bound; module parameters: mem_address=4191223808 (0xF9D10000), mem_size=2097152 (2 MiB), record_size=console_size=ftrace_size=pmsg_size=524288, dump_oops=1, ecc=0, mem_type=0. The live DT has no ramoops node and no `/dev/mem` (CONFIG_DEVMEM off).
- Panic behaviour: `kernel.panic=5`, `panic_on_oops=1`, cmdline `oops=panic`, `sec_debug.level=0`, `androidboot.force_upload=0x0` (no upload mode), `/proc/sys/kernel/sysrq`=0 (enabled to 1 for the test).
Step 2 (controlled panic): marker `M15-MARKER-20261104022648` written to /dev/kmsg (uptime 193 s), `sync; sync`, `echo 1 > /proc/sys/kernel/sysrq`, `echo c > /proc/sysrq-trigger` at ~02:26:51. The phone rebooted by itself: new boot_id (9c6089ce… -> f46dc779…), up since 02:27:09, reachable over SSH about 26 s after the panic, sysrq back to 0.
Observed:
- `/sys/fs/pstore` is EMPTY after the reboot: no console-ramoops, no dmesg-ramoops. The ramoops region at 0xf9d10000 yielded nothing.
- BUT the previous boot's log survived through Samsung's own mechanism: `/proc/last_kmsg` (2,097,152 B, mode 0440) contains the marker (2 hits, at 193.17 s and 193.24 s) and the whole crash: `el1_da -> sysrq_handle_crash -> write_sysrq_trigger -> proc_reg_write -> vfs_write`, `sec_debug: sec_debug_panic_handler`, `set magic code (0x66262564)`, DSS and ABOX panic handlers, `sec_debug: rebooting...`, `sec_reboot (0, panic)`, `set magic code (0x0)` (so a normal, not upload, boot follows). Excerpt: `reference/ramoops/last_kmsg-excerpt.txt` (24 lines, scanned: no serials, IMEI or MACs).
- New boot's command line: `sec_debug.reset_reason=4`, `sec_reset.reset_reason=4`, `sec_debug.reset_rwc=1` (previous boots showed 7 / 0): S-Boot recorded the reset kind and passed it on.
Where `/proc/last_kmsg` comes from (source, baseline tree): `drivers/samsung/debug/sec_debug_last_kmsg.c` copies the previous contents of the sec_debug buffer (`SDN_MAP_*`); that buffer lives in the S-Boot-provided region from the command line `sec_debug_next=0x800000@0x91388000` (8 MiB; neighbours `sec_avc_log=0x40000@0x91202000`, `sec_tsp_log=0x40000@0x91244000`, `sec_disp_log=0x100000@0x91286000`, `ess_setup=0xf9000000`). I first guessed it was the DSS `log_kernel` region (0xf9010000): the source says otherwise, corrected here.
Why pstore/ramoops stayed empty: NOT determined. Facts: (a) in kernel/panic.c (baseline) the panic notifier chain runs first and `kmsg_dump(KMSG_DUMP_PANIC)` (the ramoops crash-record path) runs after it; Samsung's `sec_debug_panic_handler` and the DSS handlers are in that chain and `sec_reboot` runs right after them, so the dmesg-ramoops dump may never be reached (unverified); (b) the console zone should have filled continuously yet is also empty, so S-Boot clearing 0xf9d10000, or the zones never being initialised there, are both open. Both need a 6.18 test, since /dev/mem is off and the ramoops parameters are fixed in this kernel.
Alternative chosen (acceptance: "proof it is not possible and an alternative chosen"): for 6.18 use a region whose contents are proven to survive a warm reset: the S-Boot `sec_debug_next` region (8 MiB at 0x91388000), because the baseline kernel wrote the crash log there and read it back after the reset.
DT node to reuse in M2 (proposal, NOT yet booted on 6.18; verify the address on the 6.18 boot's own `/proc/cmdline` every time):
    reserved-memory {
        /* S-Boot passes sec_debug_next=0x800000@0x91388000; contents survived a panic reboot (M1.5) */
        ramoops@91388000 {
            compatible = "ramoops";
            reg = <0x0 0x91388000 0x800000>;
            no-map;
            console-size = <0x200000>;
            record-size = <0x80000>;
            pmsg-size = <0x20000>;
        };
        /* keep the neighbouring S-Boot debug buffers from being reused */
        sec_debug_bufs@91202000 { reg = <0x0 0x91202000 0x186000>; no-map; };
    };
  Fallback (unproven, empty after the panic): ramoops at 0xf9d10000 / 0x200000 as in the current M2.1 DT. M2.1's DT node (ramoops@f9d10000) must be changed to the above before M2.4, and dt.img rebuilt with tools/dt_table.py (a follow-up for M2.4 preparation, not done here).
Reading a crash on the baseline in future: `cat /proc/last_kmsg` (root) after the reboot.
Result: PASS for the acceptance criterion "previous boot's log readable after a forced panic" (baseline, via /proc/last_kmsg); pstore/ramoops on the baseline: empty (cause unverified); DT node text recorded; 6.18 behaviour is unverified until M2.4.
