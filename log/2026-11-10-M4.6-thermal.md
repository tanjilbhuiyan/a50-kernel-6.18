# 2026-11-10 M4.6 Thermal (TMU)

## Design facts
4.14 reads temperature through ACPM (exynos9610_tmu_read -> exynos_acpm_tmu_set_read_temp, drivers/thermal/samsung/exynos_acpm_tmu.c), channel 7 (stock acpm_tmu node), request type TMU_IPC_READ_TEMP 0x02 with tzid in byte 2; reply type, tzid, temp, stat in bytes 0-3 (exynos_acpm_tmu.h). Byte 2 overlaps the ACPM sequence number (bits 21:16), which mainline uses to match replies, so the reply layout is checked first. Zones: BIG id 0, LITTLE 1, G3D 2, ISP 3. Baseline temperatures: reference/m44-buses/baseline-thermal.txt.

## Probe run 1 (12:08-12:12): firmware silent on this boot
Runner exit 0, rollback OK. Dump: reference/m46-thermal/2026-11-10-probe-dump.txt. ch7 ap_poll=1 qlen=5, queues empty; "no reply in 20000 us" to READ_TEMP tz0. In the same boot the S2MPU09 driver's first read (LDO1, 0.19 s) timed out (-62), so its probe failed and USB waited for LDO14 (no gadget). The same PMIC reads worked in every M4.2/M4.3 run. Difference: the phone had been idle on the baseline since 01:54 (overnight). Rerunning the same image on a freshly rebooted phone.

## Probe run 2 (12:13-12:16): same result, so systematic
Fresh boot, same image: READ_TEMP tz0 at 0.07 s unanswered, then the S2MPU09 driver's first read at 0.20 s timed out (-62), USB waited for LDO14. M4.2/M4.3 images (no thermal request) read the PMIC fine at 0.08-0.2 s. Reading: an uninitialised READ_TEMP stalls the ACPM firmware for the rest of the boot (UNVERIFIED how; both phones recovered normally through Download mode). 4.14 always sends TMU_IPC_INIT (type 0x01) first.
