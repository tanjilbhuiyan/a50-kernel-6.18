# 2026-11-04 M2.4 preparation: DT ramoops moved to the S-Boot sec_debug_next region (host-only)
Variable changed: nothing on the phone (not touched). DT and dt.img only.
Why: M1.5 showed ramoops at 0xf9d10000 empty after a controlled panic, while the previous boot's log survived in the S-Boot region `sec_debug_next=0x800000@0x91388000` (read via /proc/last_kmsg). First light needs a crash log region known to survive a warm reset.
Change (kernel tree, branch a50-dt, commit `1a9a67e46` on top of f7accc40b): in `exynos9610-a50.dts`
- `ramoops@91388000`: compatible "ramoops", reg <0x0 0x91388000 0x800000>, no-map, console-size 0x200000, record-size 0x80000, pmsg-size 0x20000 (about 11 crash records fit in the rest).
- `sec_debug_bufs@91202000`: reg <0x0 0x91202000 0x186000>, no-map (S-Boot's sec_avc_log/sec_tsp_log/sec_disp_log from the baseline command line plus the 8 KiB gaps between them).
- `debug_snapshot_a/ramoops@f9d10000/debug_snapshot_b` replaced by one `debug_snapshot@f9000000` reg <0x0 0xf9000000 0x1710000>, no-map (the stock block 0xf9000000..0xfa710000, header + log_* items, reserved whole; the log_pstore window is no longer special).
Checks:
- DTB builds with no dtc warnings (3,657 B, sha256 `653685a5308d65c85a757f8a46e9184cfc89e2f51ba49ad9868472c2f0295f60`).
- dt-validate (dtschema 2026.9 in a scratch venv): no output for the DTB; the validator is live: removing `reg` from the ramoops node gives "'reg' is a required property" (a first negative test that put a string in console-size was NOT flagged; not investigated, the second test proves the node is checked).
- Reserved-memory check on the built DTB: 12 regions, 0 overlaps, 0 outside RAM (memory@80000000 and @880000000).
- dt.img rebuilt with tools/dt_table.py (`build reference/stock-images/dt.img … --set 0=<dtb>`), sha256 `199df6cfa7507befba0a0c1b6abac0004265e28a755fb103a51f6b2ad633127d` (supersedes b09210d1… from M2.3), 8,388,608 B, round-trips byte-identical; header, entries, Samsung signature block, vbmeta and AVB footer identical to stock, only the DTB payload differs; `dtbo.img` unchanged (6d81cce8…). Copies, decompiled DTS, patches 0001-0003 and SHA256SUMS are in `reference/dt-6.18/`.
Known effects and open items:
- Still unverified: that mainline ramoops written at 0x91388000 survives a reset, and that the address is the same on every S-Boot run (re-check /proc/cmdline of the 6.18 boot; the first-light init prints it).
- When the baseline is booted again after first light, Samsung's sec_debug will find non-Samsung data in the sec_debug_next region (garbled /proc/last_kmsg, possibly boot-time warnings); expected to be harmless but unverified.
- Everything else from M2.1/M2.2 is unchanged: framebuffer format assumed, load address misalignment risk, PSCI reset unverified, S-Boot acceptance of the DTB/DTBO/BOOT images unverified.
Result: PASS (prepared, host-side only).
