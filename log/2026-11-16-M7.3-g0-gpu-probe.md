## G0: stopped by a too-strict gate rule

- **Image:** BOOT `src/m73/boot-g0.img`, sha256 `993d18d3a06ef87580b6b9a69c86855c22504193042c42b75e0f8d6406f157f6`
  ([inputs](../reference/m73-gpu/g0-inputs.json), [live](../reference/m73-gpu/g0-live.txt)).
- **Readings:**
  - G3D domain on (`0x3000f`).
  - TOP `GAT_CORE_G3D` and `GAT_G3D_SWITCH` = `0x00300000` (manual, on), so no enable was needed.
  - CMU_CORE G3D gates = `0x00200000`: clock value set, manual bit clear, no automatic gating.
- The probe required automatic gating, or manual mode with the value set, so it declined the bridge and read neither
  CMU_G3D nor Mali.
- With the manual bit clear a gate follows the CMU's global mode, and the value bit still enables the clock
  (`clk-exynos-arm64.c`: `GATE_MANUAL` overrides the global mode). CMU_CORE isn't registered by 6.18, so these are the
  bootloader's settings.
- **Restore:** passed; fsck clean, 6529 files ([run](../reference/m73-gpu/g0-run.txt), [fsck](../reference/m73-gpu/g0-baseline-fsck.txt)).

## Consequences for G1 (kbase r26p0 port)

- **No clock or power-domain work is needed first.** The G3D domain is on, the register path is clocked, and the GPU
  answers.
- **Fixed clock:** the GPU runs at the 260 MHz the bootloader set. No DVFS without ACPM (same root cause as M4.7). The
  platform layer must report this fixed clock and must not call `cal_dfs_*` or `cal_pd_*`.
- **Hardware to support:** Mali-G72 r0p1 (product `0x6221`, `tHEx` in b_r26p0), with 3 shader cores, one L2 and 8
  address spaces.
- **GPU memory:** the GPU's own MMU (`MMU_FEATURES`) translates its address spaces. The G3D path has no SysMMU in the stock
  DT, so kbase's page tables cover GPU memory.

## G1 sizing (host only, no boot)

- **Import:** Samsung's kbase r26p0 (`drivers/gpu/arm/b_r26p0`, release `r26p0-01eac0`, 292 files) copied unchanged to
  `drivers/gpu/arm/midgard` on the WIP kernel branch `a50-m73-g1-wip` (`6df856849`, on the D4a source). Kconfig paths
  renamed, hooked into `drivers/video/Kconfig` and `drivers/gpu/Makefile`. ARM's `memory_group_manager.h` and
  `protected_memory_allocator.h` added from the same 4.14 tree; `<linux/reservation.h>` changed to `<linux/dma-resv.h>`.
  Not built into any image.
- **Build:** separate config `src/ack-6.18/out/m73-g1` (test-7 config plus `MALI_MIDGARD`, platform name `devicetree`,
  `MALI_DMA_FENCE`, `MALI_REAL_HW`; Samsung DVFS/PM-QoS/trace/KUTF options off). Compiling `drivers/gpu/arm/midgard/`
  stops at missing headers before reaching API errors.
- **Finding 1, Samsung hooks in the core:** the kbase core includes Samsung's Exynos platform headers unconditionally:
  - `mali_kbase_defs.h:79` and `mali_kbase_jd.c:43` → `platform/exynos/gpu_integration_defs.h`;
  - `mali_kbase_core_linux.c:127` → `platform/exynos/gpu_control.h`;
  - `debug/mali_kbase_debug_ktrace_codes.h:147` → `platform/exynos/gpu_trace_defs.h`.

  About 480 Exynos/SEC references sit outside `platform/`. The generic `devicetree` platform therefore can't stand in, and
  the Exynos platform layer has to be kept and shimmed. Its hardware calls (`cal_dfs_*`, `cal_pd_*`, PM QoS, BTS, ITMON,
  TMU, ASV, `exynos_smc`) map onto a fixed 260 MHz clock and an always-on domain (G0b).
- **Finding 2, Samsung ABI additions:** `mali_kbase_ioctl.h` adds `KBASE_IOCTL_SLSI_COMBINATION_BOOST_FLAGS`,
  `KBASE_IOCTL_SLSI_VK_BOOST_FLAGS` and `KBASE_IOCTL_SLSI_NEGATIVE_BOOST_FLAGS` (ioctls 42–44). The vendor userspace may
  call them, so ARM's pristine r26p0 is not an exact ABI match. Samsung's source is the port base; the boost ioctls can be
  accepted as no-ops, since there is no DVFS.
- **Next:** stub headers for the `soc/samsung/*` and Exynos interfaces the platform layer uses, kept inside the driver
  directory. A fixed-clock, always-on implementation of the platform callbacks. Then the 4.14→6.18 API errors that remain
  once the headers resolve.
