### Source findings and their limits

1. **GIC IRQ is exposed before the core initializes its hardware.**
   `sound/soc/samsung/abox/abox_gic.c:249` requests an IRQ without
   `IRQF_NO_AUTOEN`; zeroed `data->disabled` remains false. The IRQ core
   auto-enables it (`kernel/irq/manage.c:1749`). Its handler immediately
   reads GICC and loops until a spurious ID, with no iteration bound.
   The core initializes its clocks/registers later. An early pending IRQ
   could therefore enter MMIO before the core is ready. This is a useful
   **hypothesis**, not a captured cause; the inherited code and late-bind
   success do not prove an early IRQ actually occurred. If A1g stops before
   probe entry, checkpoint GIC registration/IRQ entry and SysMMU probe.
   A future controlled IRQ-lifecycle change should keep the IRQ masked
   until hardware/handlers are ready, rather than add an arbitrary delay.
2. **The fault recovery is not proven safe.**
   `abox.c:203-211` still calls `abox_dbg_print_gpr()` before halting the DSP.
   That function still performs the same unbounded MMIO reads as before.
   A1d2's stream ends after CA7_R03 at **105.641271 s**. Moving those reads
   to a workqueue removes them from hard IRQ context; it does not prevent a
   CPU or fabric stall. Recommend avoiding GPR reads on the failed path,
   with a separately tested bounded recovery. No kernel fix applied here.
3. **GIC supplier readiness is not checked.**
   `abox.c:6120-6130` accepts an existing platform device, even when its
   driver has not bound; `abox_gic_register_irq_handler()` then dereferences
   its drvdata. A1d demonstrated the NULL dereference. This is a real
   robustness defect, but not proof of the current boot hang: Makefile and
   A1g `System.map` put the built-in GIC initcall **before** the core.
   Add proper supplier readiness/deferred probing before side effects,
   rather than claim initcall reversal without evidence.
4. **A1g is useful, but its result needs careful interpretation.**
   Its only new source change relative to A1e is the entry panic. The DSS
   dumper is a `core_initcall`, before the core's `device_initcall`, so it
   should already be armed. A successful dump pins probe entry. No dump
   alone cannot distinguish a pre-entry hang from a failure in panic/SMP
   stop/notifier/dump handling. The driver framework also resumes suppliers
   and configures DMA/IOMMU before calling the driver probe (`drivers/base/dd.c`).
   Thus "not ABOX probe = only SysMMU or GIC" is too narrow. GIC diagnostic
   labels mentioning SMC also do not prove secure calls: the selected
   `GIC_IS_SECURE_FREE` code uses direct MMIO for most initialization.
