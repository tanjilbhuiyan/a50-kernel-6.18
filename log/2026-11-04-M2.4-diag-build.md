# 2026-11-04 M2.4 diagnostic kernel (host-only; prepares attempt 2)
Why: attempt 1 left the phone on the static Samsung warning screen with no evidence of whether S-Boot started our kernel (`log/2026-11-04-M2.4-first-light.md`). A second blind try would teach nothing, so the next kernel reports its own progress through two independent channels: (1) coloured bands painted into the bootloader framebuffer, (2) markers written into DRAM that the BASELINE kernel exposes afterwards. The display alone could mislead: the stock DT says the panel is a DSI command-mode panel (`psr_mode = 2`, `trig_mode = 0`), so memory writes may not be refreshed to the screen.
Facts found on the way (also corrected in the M1.5 log): `/proc/last_kmsg` is the debug-snapshot `log_kernel` buffer (0xf9010000, 2 MiB; S-Boot writes its own boot log into its head); the baseline kernel zeroes `log_pstore` at each boot, so the empty pstore in M1.5 says nothing about S-Boot.
Patch (kernel branch `a50-diag`, on top of a50-dt, copy in `reference/m25-diag/`; DO NOT merge): `CONFIG_A50_DIAG`;
- stage 0 in `head.S` `primary_entry`, MMU off, only x9-x15 used: paints rows 0-49 red and writes at physical 0xf9030000: "A50DIAG0", the physical address the code runs at (`adr x13,.`), the DTB pointer (x0) and CurrentEL;
- stage 1 in `setup_arch()` after `early_ioremap_init()`: green rows 60-109, marker "A50DIAG1 setup_arch" at +0x100;
- stage 2 `arch_initcall`: blue rows 120-169, marker +0x200;
- stage 3 `late_initcall_sync`: white rows 180-229, marker +0x300, then 15 s of a blinking band (rows 240-289), marker +0x400, then PSCI SYSTEM_RESET (`smc 0x84000009`); if it returns, marker +0x500.
Markers sit at offset 0x20000 of log_kernel: after S-Boot's own log (~60 KB at the head) and below the baseline's saved write pointer, so `/proc/last_kmsg` (a snapshot taken early in the next baseline boot) should contain them. Framebuffer assumptions (unverified): 0xca000000, 4320 bytes/row, ARGB8888.
Build: `A50_DIAG=1 tools/m22_build.sh src/ack-6.18/out/m25-diag` (`CONFIG_LOCALVERSION=-a50-diag`). Image 7,170,056 B, sha256 `e52c8572c463f4d6986b22fd55d2290429a55b5def9a5c58b1fe74dce8287231`; verified in the binary: the stage strings, symbols a50_diag_stage1/2/3, the stage-0 machine code.

Unverified; this is a hypothesis to test, and the diag stage 0 records the address the kernel actually ran at.

## FINDING (source, not yet tested): the Samsung header magic 0xecefecef
Decoding the headers byte by byte: the baseline 4.14 Image has a non-zero value in the reserved field `res3` at Image offset 0x28: 0x00000000ecefecef. Samsung's `arch/arm64/kernel/head.S` writes it: `.quad 0xecefecef // Magic number for proca ta` (when CONFIG_PROCA is off; with CONFIG_PROCA it holds `_proca_conf_offset`, "memory info for proca ta"). PROCA is Samsung's Process Authenticator trusted app (`proca@2.0-service` opens /dev/tzdev, M1.3). Every 6.18 image built so far has 0 there; the working control (baseline header, only code0 changed) has the magic. Hypothesis: S-Boot/TEE reads that field of the kernel image and silently refuses to start an image without it; this would explain all four negatives (Tests 1-4) with the control as the only positive. Differences already ruled out: text_offset (A/B), marker order, size/image_size/ramdisk/code0 (C).

## S-Boot log read (2026-11-07): the failed boot's log is NOT recoverable; what a good boot checks

Source: `/proc/last_kmsg` read on 2026-11-07 (same 730,856-byte snapshot as after Test 7). Excerpt:
`reference/sboot/2026-11-07-sboot-good-boot-excerpt.txt`.
- The file holds 2 S-Boot sessions + 1 kernel boot: the cable-in charger-mode boot (session 1, `ro.bootmode=charger`,
  4.14 kernel) and the current normal boot (session 2, `PINFORM = 12345670`, a software reboot). No session of the failed
  Test 7 boot.
- Why: session 1 starts with `sec_debug_init_buffer: this is PIN RESET, clear all`. Every recovery from a hung test image
  is a hard key reset (Vol Down + Power), which wipes S-Boot's debug buffers. Software reboots (session 2) do not.
  => S-Boot's verdict on a failed image cannot be read via last_kmsg with the current recovery method.
- What S-Boot checks on a GOOD boot (baseline BOOT), all non-fatal:
  vbmeta hash mismatch -> `VERIFICATION_DISABLED bit is set`; `pit_check_signature (VBMETA) invalid`;
  `check_samsung_secure_info : Error validating footer (boot)` / `footer is abnormal: 6` -> BOOT "custom";
  `[AVB 2.0 ERR] authentication fail (orange)`; `[TIMA trusted boot]: SEAndroid MAGIC failure (boot.img)`;
  then UFDT DTB/DTBO selection, `Do SMC to set data for TIMA`, `Starting kernel...`.
  Nothing in this log verifies the kernel bytes themselves, so "S-Boot refuses changed Image bytes" (Test 7 reading) is
  NOT supported by S-Boot's own log. Alternatives that fit Tests 1-7 equally: S-Boot does start the kernel and something
  downstream stops it before its first store (uH hypervisor/TIMA measuring the kernel?), or a check that does not log.
  All unverified. Test 8 (one byte flipped) still discriminates "any change" vs "large change" whatever the mechanism.
- Side note: every session prints `kernel size = 0x28d8800`, which is the baseline kernel_size (0x28d8d10) rounded DOWN
  to the 2 KiB page; meaning (print only, or truncated load) unverified.

## CORRECTION (2026-11-07): Tests 1-7 negatives are NOT evidence that our code did not run

The marker channel was only ever validated WITHIN ONE BOOT (control, Test 8: cave writes, 4.14 continues, the same boot's
early snapshot exposes it). For Tests 1-7 the marker had to survive the recovery chain (hard key reset -> Download mode ->
flash -> hard reset -> often a cable-in charger-mode kernel boot -> software reboot -> snapshot). Evidence that it cannot:
- After each PIN reset S-Boot starts writing log_kernel at physical offset 0x23 (lk7 and lk8 both, lk8 after
  un-rotating by the marker position). "PIN RESET, clear all" does not zero the buffer (lk8 still holds the 94,538 s
  UT log from before the reset), it restarts the write position at 0.
- The chain from one PIN reset to the snapshot wrote 730,856 bytes in the Test 7 rollback (lk7), far past the marker at
  0x20000 (128 KiB). The bytes found at 0x20000 after Tests 5-7 were ordinary kernel log text, as this predicts.
=> The diag markers at 0xf9030000 are overwritten by our own recovery. Tests 1-7 are INCONCLUSIVE, not negative.
   Test 7 is explained without any S-Boot check: the cave ran, then the 4.14 kernel with 6 MB of corrupted data hung.
   The "S-Boot refuses changed bytes" reading (Test 7) and "S-Boot rejects 6.18 images" are withdrawn as unproven.
Next: (1) validate this prediction for free during the Test 8 rollback (marker at 0x20000 should be gone afterwards);
(2) move the markers high in log_kernel (e.g. offset 0x1c0000, physical 0xf91d0000; the recovery chain wrote ~0.7 MiB)
and validate survival across the full recovery chain with the control cave before re-running any 6.18 image.
