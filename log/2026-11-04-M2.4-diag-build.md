# 2026-11-04 M2.4 diagnostic kernel (host-only; prepares attempt 2)
Why: attempt 1 left the phone on the static Samsung warning screen with no evidence of whether S-Boot started our kernel (`log/2026-11-04-M2.4-first-light.md`). A second blind try would teach nothing, so the next kernel reports its own progress through two independent channels: (1) coloured bands painted into the bootloader framebuffer, (2) markers written into DRAM that the BASELINE kernel exposes afterwards. The display alone could mislead: the stock DT says the panel is a DSI command-mode panel (`psr_mode = 2`, `trig_mode = 0`), so memory writes may not be refreshed to the screen.
Facts found on the way (also corrected in the M1.5 log): `/proc/last_kmsg` is the debug-snapshot `log_kernel` buffer (0xf9010000, 2 MiB; S-Boot writes its own boot log into its head); the baseline kernel zeroes `log_pstore` at each boot, so the empty pstore in M1.5 says nothing about S-Boot.
Patch (kernel branch `a50-diag`, on top of a50-dt, copy in `reference/m25-diag/`; DO NOT merge): `CONFIG_A50_DIAG`;
- stage 0 in `head.S` `primary_entry`, MMU off, only x9-x15 used: paints rows 0-49 red and writes at physical 0xf9030000: "A50DIAG0", the physical address the code runs at (`adr x13,.`), the DTB pointer (x0) and CurrentEL;
- stage 1 in `setup_arch()` after `early_ioremap_init()`: green rows 60-109, marker "A50DIAG1 setup_arch" at +0x100;
- stage 2 `arch_initcall`: blue rows 120-169, marker +0x200;
- stage 3 `late_initcall_sync`: white rows 180-229, marker +0x300, then 15 s of a blinking band (rows 240-289), marker +0x400, then PSCI SYSTEM_RESET (`smc 0x84000009`); if it returns, marker +0x500.
Markers sit at offset 0x20000 of log_kernel: after S-Boot's own log (~60 KB at the head) and below the baseline's saved write pointer, so `/proc/last_kmsg` (a snapshot taken early in the next baseline boot) should contain them. Framebuffer assumptions (unverified): 0xca000000, 4320 bytes/row, ARGB8888.
Build: `A50_DIAG=1 tools/m22_build.sh src/ack-6.18/out/m25-diag` (`CONFIG_LOCALVERSION=-a50-diag`). Image 7,170,056 B, sha256 `e52c8572c463f4d6986b22fd55d2290429a55b5def9a5c58b1fe74dce8287231`; verified in the binary: the stage strings, symbols a50_diag_stage1/2/3, the stage-0 machine code.
Images (`tools/m25_diag_images.sh`, donor pinned to the baseline boot.img; header equal to the baseline except sizes): `boot-diag-A.img` sha256 `9b611efc71b8b7c6bbdac020bebf38fe4e068b67f8a9b8fb8790318cf24fb0ae` (Image header text_offset 0, as built) and `boot-diag-B.img` `0cf21b48a0f4d3811090f5df8db3dad17e3a3fc790bd23fbc77ba5b650745845` (text_offset 0x80000, the value in the 4.14 baseline Image header); 7,176,192 B each; ONE byte differs. Reader: `tools/m25_read_markers.sh PHONE_IP` (tested on the current baseline: correctly reports no markers). Bug found and fixed: `tools/m22_pack.sh` globbed its donor and matched the later `baseline/m24-pre-flash/boot.img`; the donor path is now pinned (the first-light image still reproduces d45d0b6b…).
Why text_offset: the 4.14 Image header says text_offset 0x80000 and the 4.14 kernel needs to run inside DRAM (0x80000000 base), while the boot.img says kernel_addr 0x10008000 (0x10000000 is SoC register space, not DRAM), so S-Boot very likely relocates the kernel to DRAM base + text_offset = 0x80080000. The 6.18 header says 0, which would put it at 0x80000000, on top of the reserved `sec_debug_magic` page. Unverified; this is a hypothesis to test, and the diag stage 0 records the address the kernel actually ran at.
Test plan (each step changes one thing; the phone currently has the STOCK DTB/DTBO, so only BOOT is flashed):
1. boot-diag-B + stock DT. Observe: bands on the screen; whether the phone restarts about 20-30 s after the kernel starts (PSCI reset worked = proof of life); then roll back BOOT only and run `tools/m25_read_markers.sh`.
2. If dead, boot-diag-A + stock DT (alive => the text_offset change broke it, odd; dead too => look further).
3. Only after something is alive: our DTB/DTBO with the working image (the DT signature question), then the full first-light init.
## Test 1 result (2026-11-04 03:33-03:50): boot-diag-B + stock DT, BOOT only: NO sign of life
Flash: `heimdall flash --BOOT boot-diag-B.img --no-reboot` ok (03:33). Owner restarted (off-charging icon first, then Vol Down+Power): vibration, Samsung logo and warning screen, then static for 2 full minutes: no bands, no blinking, no restart. Rolled back with `heimdall flash --BOOT baseline boot.img` (03:41, ok), baseline booted, SSH back.
Marker read-back (`tools/m25_read_markers.sh`): NO A50DIAG markers. Checked the raw snapshot: the bytes at the stage-0 offset (file offset 0x20000 of the 682,001-byte /proc/last_kmsg) are OLD baseline kernel log text (`ufshcd_populate_vreg…`, `exynos-ufs…`, `TZDEV>…`), i.e. stage 0 did not write there. Disassembly of the diag vmlinux confirms the stage-0 code is what was intended.
Facts learned (not assumptions):
- The baseline 4.14 kernel runs at physical `0x80278000` ("Kernel code" in /proc/iomem; System RAM starts at 0x80000000). So S-Boot's placement rule is NOT "DRAM base + text_offset (0x80080000)" as I assumed; the text_offset patch of image B rested on a wrong premise. The rule is unknown.
- S-Boot loads the Samsung uH hypervisor before the kernel (`[uH] load hypervisor`, signature valid), logs `AVB 2.0 ERR ... (orange)` and `SEAndroid MAGIC failure (boot.img)` even for the working baseline, and selects DT and overlay by revision: `[UFDT] Little Find DTB Entry[0]: Rev:(S:0, E:255, X:0, D:6)`, `Find DTBO Entry[5]: Rev:(S:6, E:255, X:0, D:6)` (so the custom[0]/custom[1] fields kept in M2.3 are what it matches on).
- /proc/last_kmsg holds only old S-Boot sessions (identical in two snapshots), so it cannot show S-Boot's account of the diag boot; the buffer apparently stops being updated after boots that end without a clean kernel shutdown. No inference about S-Boot's behaviour can be drawn from its absence.
Flaw found in the diagnostic: stage 0 painted 216 KB of framebuffer BEFORE writing its marker. If the first store to 0xca000000 faults (for example because of the hypervisor's stage-2 protection), no marker is written, so "no marker" does not distinguish "kernel never entered" from "first store faulted". Fix: the marker stores come first, a second marker after the paint loop shows whether the loop completed.
Conclusion so far: either the kernel was not entered, or its very first store to the framebuffer faulted; this test cannot tell which. Result: INCONCLUSIVE, with a diagnostic design flaw fixed in the next version (v2).

## CONTROL RESULT (2026-11-04 03:59-04:03): the control image booted Ubuntu Touch AND left the marker
Flash `boot-control.img` ok (03:59:22); owner restarted; Ubuntu Touch came up (kernel 4.14.194, up since 04:00:38). `tools/m25_read_control.sh`: marker found at snapshot offset 0x20000 (as designed). Decoded (what S-Boot hands to the kernel, measured, not assumed):
- the cave's `adr` PC = 0x82a18028 (MMU off, physical) => the 4.14 Image is loaded at physical 0x80140000 (= DRAM base + 0x140000), NOT 2 MiB-aligned;
- x0 = 0x8a000000 (the DTB S-Boot patched, matches `Updating device tree @0x8a000000` in its log); x1 = 0x80000000 (DRAM base); x2 = 0x140000 (load offset from DRAM base); x3 = 0x80140000 (the load/entry address). Samsung passes x1-x3 non-zero, unlike the standard arm64 boot protocol (which wants them 0);
- CurrentEL = EL1; the stores landed at physical addresses, so the MMU is off.
Consequences:
1. S-Boot accepts and enters a modified Image; the marker channel (physical 0xf9030000 = log_kernel + 0x20000, read via /proc/last_kmsg) works with a foreign writer. Therefore the absence of markers in Test 1 (flawed v1: marker after the paint) and Test 2 (v2 image A, text_offset 0, marker FIRST) is a real negative for those images: the 6.18 kernel's first instructions did not run.
2. The untested combination is v2 + image B (text_offset 0x80000, the baseline's header value): Test 1 used B only with the flawed v1. S-Boot may use or validate the header's text_offset/placement fields; A and B differ in exactly that byte.
3. Even once stage 0 runs, the 6.18 kernel will meet a load address that is not 2 MiB-aligned (0x80140000, text_offset 0), which the arm64 boot protocol does not allow. Likely fix: a tiny relocation stub at the entry that copies the Image to a 2 MiB-aligned address (for example 0x80A00000, which does not overlap the 7.6 MiB image at 0x80140000..0x808B4000) and jumps there with x0 preserved.

## FINDING (source, not yet tested): the Samsung header magic 0xecefecef
Decoding the headers byte by byte: the baseline 4.14 Image has a non-zero value in the reserved field `res3` at Image offset 0x28: 0x00000000ecefecef. Samsung's `arch/arm64/kernel/head.S` writes it: `.quad 0xecefecef // Magic number for proca ta` (when CONFIG_PROCA is off; with CONFIG_PROCA it holds `_proca_conf_offset`, "memory info for proca ta"). PROCA is Samsung's Process Authenticator trusted app (`proca@2.0-service` opens /dev/tzdev, M1.3). Every 6.18 image built so far has 0 there; the working control (baseline header, only code0 changed) has the magic. Hypothesis: S-Boot/TEE reads that field of the kernel image and silently refuses to start an image without it; this would explain all four negatives (Tests 1-4) with the control as the only positive. Differences already ruled out: text_offset (A/B), marker order, size/image_size/ramdisk/code0 (C).
